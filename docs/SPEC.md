## 0. Принципи
1. **Персонаж, а не чат-бокс.** Усе, включно з AI, керує тілом персонажа: позою, емоцією, дією.
2. **Живий без мережі.** Без ключа LLM і без Ollama персонажі повністю працюють: поведінка, реакції, репліки з шаблонів, фокус.
3. **Не заважати.** Click-through поза тілом, ховається у fullscreen, глобальні ліміти непрошених реплік, кожну реакцію можна вимкнути.
4. **Приватність за замовчуванням.** Нічого не йде в мережу без явної дії, телеметрії немає.
5. **Лише оригінальні персонажі в дистрибутиві** (ADR 005). Захищені IP — тільки особистий імпорт користувача.
6. **Виміряне, а не задеклароване.** Бюджети CPU/RAM перевіряються `pnpm perf` на зібраній збірці.

## 1. Цілі та не-цілі

**Цілі v1**
- **Один активний персонаж** живе поверх вікон і не блокує кліки поза своїм тілом. Персонажа можна швидко змінити (трей, налаштування, хоткей) — D-8.
- Багата поведінка: десятки занять, реакції на курсор, рух вікнами й краями екрана.
- Реальна користь: AI-чат у характері з read-only tools про систему, фокус-таймер, нагадування.
- **Dev companion:** реакції на події Claude Code (hooks) і локальний MCP-сервер.
- **MCP-клієнт (D-24, ADR 013):** користувач підключає власні MCP-сервери, і персонаж у характері користується їхніми tools — лише увімкненими, з підтвердженням кожного виклику, що не є read-only (§6.8).
- 8 вбудованих оригінальних персонажів (4 жіночі, 4 чоловічі; D-18) + імпорт скін-паків і GIF.
- Бюджет у простої: **< 2% CPU**, **≤ 280 MB приватної пам'яті** сумарно по всіх процесах (середнє; working set лише для довідки — він подвійно рахує спільні сторінки). Зібрана збірка, `pnpm perf`. ADR 007.

**Не-цілі v1**
- macOS і Linux (після v1; платформо-залежний код за інтерфейсами, ADR 001).
- Акаунти, синк, бекенд, маркетплейс скінів.
- Будь-яке керування системою: kill процесів, shell-команди, зміна файлів чи налаштувань ОС — вбудованих таких tools немає. Що вміє MCP-сервер, підключений користувачем, відбувається лише після його «Дозволити» на кожен виклик (§6.8).
- Голос (TTS/STT): інтерфейс закладається, реалізація після v1.

## 3. Архітектура

```
┌──────────────────────────── Main process ────────────────────────────┐
│ AppController                                                        │
│  ├─ core (pure): BehaviorEngine · Physics · Mood · Throttle ·        │
│  │               FocusClock · ActivityPicker · Switch                │
│  ├─ WindowManager   (stage/overlay, menu, chat, settings)            │
│  ├─ Sensors         (system 2–5 s, desktop/windows, idle, fullscreen,│
│  │                   cursor 30 Hz лише коли курсор біля персонажа)   │
│  ├─ Scheduler       (один таймер до `wakeAt` → події в core)         │
│  ├─ AIService       (AI SDK, tools, persona, memory, budget)         │
│  ├─ DevCompanion    (hooks endpoint, MCP server, git/CI)             │
│  ├─ CharacterRegistry (built-in + imported packs, validation)        │
│  ├─ Storage         (electron-store + SQLite, migrations)            │
│  └─ Hotkeys · Tray · Updater · AutoLaunch                            │
└──────────────────────────────────────────────────────────────────────┘
        │ typed IPC (contextBridge, zod-validated, src/shared/ipc.ts)
┌───────▼─────────────┐  ┌───────────────┐  ┌────────────────┐
│ Stage renderer      │  │ Chat renderer │  │ Settings       │
│ PixiJS: animator,   │  │ React, stream │  │ React          │
│ hit-test, fx, drag  │  │ markdown      │  │                │
└─────────────────────┘  └───────────────┘  └────────────────┘
```

**Правила:**
- Рішення про поведінку ухвалює лише `src/core` (одне джерело істини). Main підключає сенсори й таймери, renderer малює і шле ввід.
- Core чистий: `now` і RNG передаються ззовні, жодних імпортів Electron/Node/DOM/Pixi (ADR 002).
- Core описує рух аналітично (ходьба — ціла кількість кроків, політ — замкнена формула траєкторії); renderer обчислює позицію тим самим чистим семплером `shared/motion.ts` від часу. Ходьба рухається кроками, прив'язаними до кадрів анімації, без інтерполяції (ADR 010). Core не знає про кадри.

### 3.1 Вікна (ADR 007: варіант A)
- **Обрано — варіант A, Stage overlay** (ADR 007, спайк S1: плавніше на око власника; ціна — ~66 MB GPU-пам'яті): одне прозоре вікно на весь `workArea` дисплея: `transparent`, `frame: false`, `alwaysOnTop: 'screen-saver'`, `skipTaskbar`, `focusable: false`, `hasShadow: false`. Персонаж — спрайт у canvas. Плавний рух, FX без додаткових вікон.
- **Відхилено — варіант B** (лишається запасом, якщо overlay колись стане проблемою): маленьке вікно на персонажа, рух інтерполюється в renderer, main рухає вікно на 30–60 Hz лише під час руху.
- Спайк S1 (`docs/plans/spikes/s1-windows.md`): A 250 MB / B 185 MB приватної пам'яті, CPU у спокої майже однаковий, A плавніший на око. **Сумісний режим** (`--compat-mode`, програмний рендер) — ручний перемикач для GPU з чорним фоном (electron#40515); у A ходьба в ньому ~16% CPU, тож до M1 обмежити перемальовування або fps.
- **Click-through:** `setIgnoreMouseEvents(true, { forward: true })`. Renderer на `mousemove` робить hit-test по альфа-каналу поточного кадру. Над непрозорим пікселем він просить main вимкнути ignore і повертає ignore, коли курсор пішов.
- **Menu window (ADR 015, M1):** радіальне меню по правому кліку на персонажі (UI-GUIDE §3) — окреме прозоре безрамкове **focusable** вікно поверх stage (`screen-saver` + `moveTop()`), React + CSS Modules, вбудовані шрифти; квадрат ≈ 2 × (175 + 54 + запас) DIP з центром на персонажі, обмежений робочою областю; пункти — на дузі, що вміщується в робочу область (`radialLayout()`). **Створюється при відкритті й знищується при закритті** (Esc, втрата фокуса, вибір пункту, клік по прозорій ділянці) — у простої вікна немає. Stage лишається не-focusable і без UI-тексту.
- **Chat window:** окреме focusable-вікно біля активного персонажа, створюється ліниво і ховається.
- **Settings window:** звичайне вікно, створюється і знищується щоразу.
- **Шар (D-9):** перемикач у треї й налаштуваннях — «Поверх усіх вікон» (за замовч., `alwaysOnTop: 'screen-saver'`) або «Лише на робочому столі» (без always-on-top, вікно не виходить на передній план, персонаж видно там, де відкритий стіл; поверхні вікон у цьому режимі вимкнені — ходить лише панеллю задач, а з M1b ще й краями екрана). Вбудовування в шар шпалер за іконками (WorkerW) — не робимо.
- Multi-monitor: stage на одному дисплеї (вибір у налаштуваннях), реакція на `display-added/removed/metrics-changed`.

### 3.2 IPC
- Контракти в `src/shared/ipc.ts` як zod-схеми. `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
- Канали M1 (план M1, контракти й тести на обох кінцях):
  - `stage:input` (renderer → main) — union: `pointer{x,y}` (≤ 30 Hz і лише поблизу персонажа), `pointer-leave`, `click`, `drag-start`, `drag-end{x,y,vx,vy}` (скінченні числа в межах), `context-menu`; погладжування й тицяння розпізнає core, не renderer;
  - `stage:frame-state` (main → stage) — ідемпотентний знімок `{seq, key, anim, facing, playback, motion, fx[]}`; перезавантажений renderer просто застосовує його знову;
  - `stage:loaded` (stage → main) — `{key, ok}`, коли атлас готовий або не завантажився (зміна персонажа);
  - `stage:characters` (main → stage) — пакети з якорями FX на анімацію й атласом FX, позначені `active` | `incoming`;
  - `menu:state` (main → menu) — пункти з `enabled`/причиною, персонажі (ключ, i18n-ім'я, мініатюра), поточний, стан переходу; `menu:action` (menu → main) — union `switch{key}` | `hide` | `settings` | `close`.
- Канали далі: `chat:send`, `chat:stream`, `chat:abort`, `settings:get/set`, `characters:list/import/remove`, `system:snapshot`, `focus:*`.
- Кожне повідомлення валідується на вході в main. Renderer не отримує сирих даних сенсорів, лише те, що треба для відображення.

### 3.3 Рендер і бюджет
- Анімації піксель-арту 6–12 fps. Pixi `ticker.maxFPS` залежить від поточної дії: ~12 у спокої, 30–60 під час фізики й drag, 2 fps або пауза у `sleep`/`hidden`. Рендер лише при зміні кадру.
- **Розмір (D-10):** ціль задається в логічних px (DIP), фізичний масштаб — ціле число: `scale = max(2, round(targetDip × scaleFactor / scaleRef))` (`scaleRef` — висота фігури, §5.1), фігура не вище `maxFraction` (0,25, ADR 012) висоти робочої області; перерахунок на `display-metrics-changed`. Пресети S 96 / **M (за замовч.) ≈ 136 DIP** (≈ 3 см на 15,6" 1080p @125%) / L 176 DIP (ADR 012, `scaleRef` 48: на 1080p @125% — ×3/×4/×5, на 100 % — ×2/×3/×4), плюс точне налаштування кроками цілого масштабу; числа — у `src/content/`.
- Nearest filtering, цілі позиції; спрайт малюється рівно `frameH × scale` фізичних px (чіткість при 125/150%).
- Один атлас на персонажа (≤ 2048²), спільний атлас FX.

## 4. Поведінка (src/core)

### 4.1 Стейт-машина
Стани: `idle`, `walk`, `run`, `climb`, `sit_edge`, `hang`, `peek`, `sleep`, `drag`, `fall`, `land`, `talk`, `think`, `activity:<id>`, `react:<event>`, `menu`, `switch_out`, `switch_in`, `focus`, `hidden`. Стани — розмічене об'єднання (discriminated union) з `since`/`until`. `run`, `climb`, `hang`, `peek` потребують арту, якого ще немає, — вони в арт-проході **M1b** (§12, D-27); до того ці анімації лише fallback і ядро в ці стани не переходить. `menu` (M1) — персонаж уважно дивиться фронтально, поки відкрите радіальне меню.
Кожен стан має `enter / exit`, мін/макс тривалість і ваги переходів. **Планування за дедлайнами (D-27):** `step(state, event, now)` чисте, а новий стан несе `wakeAt` — найближчий момент, коли ядру знову треба щось вирішити. Main тримає один таймер до `wakeAt` (не частіше 10 Hz) і не будить ядро, коли нічого не заплановано; сенсори й ввід приходять подіями. Той самий seed і ті самі події дають байт-ідентичний журнал ефектів. Плавність дає renderer (§3).

Переривання за пріоритетом:

| Пріоритет | Подія | Реакція |
|---|---|---|
| 100 | Користувач тягне / кидає | `drag` → `fall` з інерцією кидка, відскок від країв → `land` |
| 95 | Fullscreen / демонстрація екрана / DND / тихий режим | `hidden` (або мінімальний режим у кутку) |
| 92 | Зміна персонажа (§4.4) | `switch_out` → `switch_in` (drag перериває й одразу завершує перехід) |
| 90 | Claude Code чекає дозволу (`PermissionRequest`) | `react:needs_you` — махає, бульбашка (§7) |
| 80 | Батарея < 15% без зарядки | `react:low_battery` |
| 70 | CPU > 90% протягом 20 с | `react:overheat` + пропозиція показати топ-процеси |
| 70 | RAM > 90% | `react:heavy` |
| 65 | Claude Code: `Stop` / `PostToolUseFailure` / тести впали чи пройшли | `react:agent_done` / `react:agent_failed` |
| 60 | Диск < 10% вільно (раз на день) | `react:disk_full` |
| 60 | Відкрите радіальне меню (правий клік) | `menu` — реакції курсора чекають, drag перемагає |
| 55 | Курсор: різкий рух поруч / погладжування / тицяння | `react:startle` / `react:petted` / `react:poked` |
| 50 | Pomodoro / нагадування | `talk` з повідомленням |
| 40 | Idle користувача ≥ `USER_IDLE_SLEEP_MS` (за замовч. 5 хв), блокування екрана, сон ПК | `sleep` (будить активність, розблокування, клік) |
| 10 | Нічого | вибір заняття (§4.3) |

**Анти-спам** (як у push-платформах: пріоритет, cooldown, тихі години):
- кожна реакція має cooldown (за замовч. 30 хв);
- **виняток (D-27):** реакції на курсор (`startle`, `petted`, `poked`) ініціює сам користувач і вони мовчазні (лише анімація й FX, без репліки), тому їхній cooldown — секунди (`CURSOR_REACTIONS.*.cooldownMs`); якщо така реакція колись отримає репліку, на репліку діє глобальний ліміт нижче і тихі години;
- глобально не частіше 1 непрошеної репліки на 10 хв;
- тихі години;
- черга з дедуплікацією.
Подія перериває поточний стан, лише якщо її пріоритет вищий; за рівного — у чергу (одна на вид, найновіша перемагає); `hidden` відкидає всі реакції й репліки. Пороги й cooldown лежать у `src/content/`, а не в логіці.

### 4.2 Фізика і простір
- «Підлога» — верхній край панелі задач (`workArea`). Поверхні: підлога, верхні краї вікон (sit/walk), бокові краї вікон (climb/hang), краї екрана (peek).
- **M1 (D-27):** підлога + видимі верхні краї вікон (лише ділянки, не закриті вікнами вище, у межах робочої області, із запасом висоти для спрайта, не вужчі за `SURFACE_MIN_WIDTH_ART`). На верхній край персонаж потрапляє кидком/drag або сходячи з вищого краю на нижчий. Бокові краї (climb/hang) і краї екрана (peek) — **M1b**; тип поверхні вже розмічене об'єднання, готове до них.
- `DesktopSensor` дає bounds видимих вікон через власний Win32-біндинг на **koffi** (ADR 014): `EnumWindows` у z-порядку, видимі межі DWM (`DWMWA_EXTENDED_FRAME_BOUNDS`), без cloaked, згорнутих, tool- і shell-вікон та без власних вікон Pixmates. **Заголовки вікон і доступ до процесів не читаються.** Межі валідуються в main (скінченні числа, ≤ 64 вікна, ≥ 1 px), переводяться у DIP, а core бачить лише непрозорі id (HWND не виходять за межі main). Зміни — через `SetWinEventHook` або опитування (вирішує спайк S4); частота задається ядром (часто — лише поки персонаж на вікні; на підлозі ≤ 1 Hz; у `sleep`/`hidden`/режимі «лише на столі» — вимкнено). Якщо вікно під персонажем рухається, згортається чи закривається — `fall` (≤ 250 мс).
- Політ — замкнена формула `p(t) = p0 + v·t + ½·g·t²`, сегменти між відскоками від стін і стелі; приземлення — на першу поверхню, яку траєкторія перетинає вниз. Числа (гравітація, відскок, межа швидкості кидка, жорстке приземлення) — у `src/content/physics.ts`, в арт-px, щоб відчуття не залежало від розміру.
- Гравітація, швидкість ходьби, інерція кидка, відскок. Межі екрана. Персонажі не перекривають одне одного (м'яке розштовхування).
- **Ракурс (D-16):** пересування вздовж поверхонь (`walk`, `run`, `climb`) — у ракурсі три чверті (3/4), намальованому обличчям праворуч; ліворуч — дзеркало в рантаймі за полем `facing` (§5.1). Перед рухом — `turn` (фронт → 3/4), після зупинки — `turn` у зворотному порядку кадрів. Решта станів (idle, talk, емоції, sit_edge, sleep, drag, fall, land) — фронтально, без дзеркала. Голова під час ходьби не хитається вбік (лише вертикальний bob ≤ 1 px).

### 4.3 Заняття (activities)
Заняття — це **дані в маніфесті персонажа**: `id`, анімація(ї), умови (час доби, настрій, поверхня, фокус-режим, наявність інших персонажів), вага, тривалість, cooldown.
- Спільні: читає, пʼє чай, позіхає, потягується, сидить на краю вікна, спить на вікні, лізе по краю, визирає з-за краю екрана, ходить панеллю задач.
- Фірмові: 3–5 на персонажа (§5.3).
- Курсор (усі): стежить очима, лякається різкого руху, ганяється або «ловить» курсор, погладжування (коло курсором над персонажем), тицьнути, drag з теліпанням ніг, кидок з інерцією. **M1:** переляк (`startle`), погладжування (`petted`, підвищує настрій), тицяння (`poked`; серія тицянь → `worried`), drag і кидок; стеження очима, погоня й фірмові заняття — **M1b** (потрібен арт).
- **M1 — спільний набір із наявних анімацій:** стоїть, переминається, прогулянка до випадкової досяжної точки, сидить на краю (лише верхній край вікна), думає, махає. Решта спільних занять зі списку вище — з арт-проходом M1b.
`ActivityPicker` вибирає зважено з урахуванням недавніх занять, щоб не повторюватись. RNG детермінований, із seed.

### 4.4 Зміна персонажа (D-8)
На екрані завжди рівно один активний персонаж. Зміна — з трею (список персонажів), радіального меню (галерея), налаштувань або хоткея «наступний» (`Ctrl+Alt+N`, D-27; конфлікт хоткея показується в треї, як для `Ctrl+Alt+P`).
- Перехід: `switch_out` поточного (іде за край екрана, якщо найближчий край не далі `SWITCH_WALK_MAX_MS` ходьби, інакше зникає в клубі диму) → `switch_in` нового (з'являється з того ж місця) — до 2 с, переривається drag-ом (тоді новий персонаж одразу в руці). Якщо атлас нового не завантажився за `SWITCH_LOAD_TIMEOUT_MS`, лишається поточний, помилка — в лог.
- `mood`, `affinity` і памʼять зберігаються окремо для кожного персонажа; історія чату — спільна, з позначкою персонажа.
- Активний персонаж зберігається між запусками. Атлас попереднього вивантажується після переходу (бюджет RAM).

### 4.5 Настрій (легкий тамагочі)
- `mood` (0–100) і `affinity` (0–100) для кожного персонажа окремо, у SQLite з M1 (D-27): таблиця `character_state(character_id, mood, affinity, updated_at)`, міграція `001`; запис із debounce, а також при зміні персонажа й виході. Налаштування (активний персонаж, розмір, шар) — в `electron-store`. Повернення до 50 рахується аналітично від `updated_at`.
- Росте від погладжування, завершеного Pomodoro, розмов. Повільно повертається до 50.
- Впливає лише на вибір занять, анімацій і реплік. **Без** штрафів і нав'язливих механік.

## 5. Персонажі

### 5.1 Формат пакета (runtime)
Runtime бачить лише спрайтшити + маніфест. Вбудовані персонажі збираються в цей формат із ригу (§5.2), імпортовані приходять готовими.
```
foxy.pixmate/   (zip з розширенням .pixmate або тека)
  manifest.json
  sprites/*.png
  sounds/*.ogg        (опційно)
  lines.uk.json  lines.en.json   (опційно)
```
`manifest.json` (скорочено):
```json
{
  "id": "com.example.foxy",
  "name": "Foxy",
  "version": "1.0.0",
  "author": "…",
  "frameSize": { "w": 48, "h": 56 },
  "anchor": { "x": 0.5, "y": 1.0 },
  "scaleRef": 48,
  "animations": {
    "idle": { "file": "sprites/idle.png", "frames": 6, "fps": 6, "loop": true },
    "sit_edge": { "file": "sprites/sit.png", "frames": 6, "fps": 6, "loop": true, "origin": { "x": 0, "y": 0 }, "anchor": { "x": 0.5, "y": 0.87 } },
    "walk": { "file": "sprites/walk.png", "frames": 8, "fps": 10, "loop": true }
  },
  "fallbacks": { "react:*": "idle", "activity:*": "idle", "climb": "walk" },
  "emotions": ["happy", "think", "worried", "proud", "sleepy"],
  "activities": [
    { "id": "read", "anim": "read", "where": ["floor", "window_top"], "weight": 3, "minMs": 20000, "maxMs": 60000 }
  ],
  "persona": "Короткий опис характеру для системного промпту (опційно)"
}
```
- Обов'язкові анімації: `idle`, `walk`. Решта — через `fallbacks`.
- `origin` (опційно, за замовчуванням 0,0): лівий верхній кут горизонтальної смуги кадрів у `file`, тож усі анімації можуть жити в одному атласі (вбудовані: один атлас ≤ 1024² на персонажа).
- `scaleRef` (опційно, 8…`frameSize.h`, за замовчуванням `frameSize.h`): висота фігури, за якою рахуються масштаб S/M/L і обмеження частки робочої області; рядки над нею — прозорий запас (headroom, ADR 009). Вбудовані: кадр 48 × 56, `scaleRef` 48 — однаковий для всіх (ADR 009, ADR 012; дорослий 56 × 72 / 66 з ADR 011 скасовано).
- `anchor` на анімації (опційно, 0…1): власна точка опори замість пакетної (напр. `sit_edge` — на сидінні, `hang` — на руках у M1); в IPC — з M1.
- `facing` на анімації (опційно, `front` | `right` | `left`, за замовчуванням `front`): куди дивиться намальований персонаж. Рантайм (M1) дзеркалить анімацію, якщо `facing` протилежний напрямку руху; `front` не дзеркалиться. Вбудовані: `walk`, `turn` — `right` (D-16). Ракурси — поняття ригу, у пакеті лише смуги кадрів + `facing`.
- Вбудовані пакети мають id `pixmates.<id>` (тека = id); імпорт не може використати цей префікс, пакована збірка читає лише `pixmates.*`.
- Імпорт **одиночного GIF/APNG** → авто-пак з однією анімацією.
- Валідація zod; ліміти ≤ 50 MB, ≤ 4096 px на текстуру; лише png/webp/gif/ogg/mp3. Розпаковка в `userData/characters/<id>` із захистом від zip-slip; без JS; `persona` і репліки — недовірений текст (§6.5).

### 5.2 Модульний риг (вбудовані персонажі, ADR 004)
- **Деталізація — головна вимога до арту (D-10):** дуже детальний і стильний піксель-арт. Тому кадр більший за класичні 32×32: **кадр 48 × 56** (ADR 009, ADR 012 / D-20: фігура 48 × 48, стопи на рядку 46, вісь x = 24, 8 рядків запасу зверху). Над маківкою — запас висоти, щоб роги, вуха, капелюх, чуб і верх стрибка ніколи не обрізались; рядок 0 завжди прозорий (тест). Зміна висоти кадру — лише рішенням власника. Більше деталей у кадрі замість крупніших пікселів.
- Спільний скелет на обраний кадр. Слоти: голова, тулуб, руки, ноги / колесо, хвіст / крила / плащ, аксесуар.
- Анімації описані **один раз** як рух частин (ключові пози по кадрах) і застосовуються до всіх персонажів. Персонаж = частини + палітра + фірмові анімації.
- **Увесь арт — кодом (D-11):** власник не малює, художника немає. Частини — генератори й авторські піксель-маски в коді (`assets-src/`). Палітра — спільна майстер-палітра + рампа персонажа. Результат: `resources/characters/<id>/` (згенероване, не редагується).
- Якість приймає `art-director` за скриншотами на реальних шпалерах (світлих і темних).
- **Стиль — піксельне аніме, chibi-пропорції (D-13, D-20), для всіх персонажів:** ~2–2,5 голови, велика голова, виразні аніме-очі ~⅓ обличчя (ART-BIBLE §11.1–11.2); дорослі пропорції D-19 / ADR 011 скасовано (ADR 012). **«Суворий погляд»** — опція обличчя на персонажа (`goth`, `ronin`, `coder`; ART-BIBLE §11.9): повіка ріже верх райдужки, брови під кутом і видимі, рівний або стиснутий рот, менший відблиск, рум'янець лише в `petted`; пропорції не змінюються; емоції (радість, тривога, переляк, `petted`, сон) знімають суворість, тож персонаж не виглядає злим постійно. **Маска рота** — опційний слот (`ronin`: menpō): ховає рядки рота, на виразах зі списку (`petted`, `happy`, `sleep`) опускається на шию; поки маска вдягнена, `talk` — лише очі й брови. **Багатий костюм** (D-20, ART-BIBLE §12): шари одягу, одна фірмова деталь, контраст матеріалів (лак, метал, тканина, шкіра), оздоби читаються в 1×. Стиль затінення — «anime soft» (6–7 тонів, м'яке моделювання, ручний AA, rim; ADR 009, cel відкинуто); волосся пасмами з гострими кінчиками і смугою-відблиском («ангельське кільце»); аніме-значки емоцій як FX (краплі поту, «венка» злості, штрихування рум'янцю, ^^ і >< очі). Нелюдські персонажі — аніме-маскоти (очі-екрани/вогники, кругліші форми). Стиль — не IP: оригінальність (ADR 005) перевіряється в кожному рев'ю.
- **Якість — максимум для арту кодом (D-11):**
  - авторські піксель-маски для облич і ключових деталей (очі, брови, рот — окремий шар на кожну емоцію), процедурні матеріали лише для тканини, металу, каменю, хутра;
  - hue-shifted рампи 5–7 тонів на матеріал, selective outline (кольоровий, світліший з боку світла), rim light для темних шпалер, ручний anti-aliasing по контуру, дизеринг лише як фактура;
  - вторинний рух (волосся, хвіст, плащ, стрічки) — фізика по кадрах із квантуванням у пікселі; squash & stretch, anticipation, follow-through; дихання в idle;
  - субпіксельна анімація (зсув кольору замість зсуву форми) для дрібних рухів;
  - референс-борд якості в `docs/art/` (сучасний HD-піксель-арт, лише як планка якості, без копіювання);
  - арт-гейт: `art-director` до 3 раундів на кожен персонаж + підпис власника; чекліст «краси» в ART-BIBLE.
- Мінімальний набір анімацій: `idle`×2, `walk`, `turn`, `run`, `climb`, `sit_edge`, `hang`, `peek`, `sleep`, `drag`, `fall`, `land`, `talk`, `think`, `happy`, `worried`, `wave`, `petted`, `startle` + фірмові. У M-ART — 16 (без `run`, `climb`, `hang`, `peek`; вони й фірмові — у M1, до того через `fallbacks`).
- **Ракурси ригу (D-16, ADR 010):** `front` і `q34` (три чверті, обличчям праворуч, ліворуч — дзеркало). У `q34`: `walk` (крок уперед-назад уздовж руху, голова стабільна) і `turn` (2 кадри: голова випереджає тіло); у M1 — `run`, `climb`. Для `q34` персонаж має власні маски голови, обличчя (мінімум `neutral`, `blink`) і аксесуарів; дальня рука й нога — за тулубом. Усі перевірки (headroom, шви, обличчя, рука над тулубом, дзеркало) діють і на кадри `q34`.
- FX кодом поверх: «Zzz», краплі поту, серця, знак питання, клуб диму, іскри.

## 6. AI в персонажі

### 6.1 UX
- Відкриття: глобальний хоткей (`Ctrl+Shift+Space`, з перевіркою конфлікту), клік по персонажу, трей.
- Бульбашка біля персонажа, стрімінг, персонаж у `think` під час tool calls і в `talk` під час відповіді.
- Історія розмов (SQLite), «нова розмова», копіювання, Markdown-рендер коду (без HTML).
- Швидкі дії-чипи: «Що гальмує?», «Скільки місця?», «Поясни скопійоване», «Почни Pomodoro».
- **«Поясни цю помилку» з буфера (M2, D-24):** чип «Поясни скопійоване» (і пункт трею) — єдиний шлях до `get_clipboard_text`. Буфер читається лише в main і лише після натискання. Без кліку tool не пропонується моделі.
  - Текст недовірений: обрізається до `CLIPBOARD_MAX` символів (`src/content/`), іде в промпт розміченим блоком, вмикає правило «забруднення» (§6.8). Порожній буфер або не текст → шаблонна репліка, без LLM.
  - Відповідь у характері: що означає помилка, ймовірна причина, кроки виправлення; код — Markdown-блоком у чаті (без HTML). Тіло: `think` під час відповіді, наприкінці `action: point_at_chat`. Нових поз не треба.
  - Команди з відповіді лише показуються як текст (§6.4), апка їх не виконує.
- **Візуальний стиль UI (D-26):** напрям A «Pixel-native», інтерфейс як частина гри. Токени, компоненти (бульбашка, чипи, слід tools, картка підтвердження MCP, радіальне меню, галерея, налаштування) і стани — у `docs/design/UI-GUIDE.md`.
  - Правила читабельності:
    - репліки, повідомлення, описи налаштувань і тіло картки підтвердження — лише Rubik, від 15 px (у чаті 16 px);
    - піксельні шрифти (Tiny5, Press Start 2P) — лише для заголовків, міток, кнопок і короткого хрому;
    - назви tools і серверів, команди та JSON-аргументи — моноширинним шрифтом;
    - WCAG AA у світлій і темній темах, видимий фокус.
  - Картка підтвердження MCP показує повний JSON моноширинним шрифтом у контрастній рамці та бейдж «змінює дані».

### 6.2 Відповідь = текст + тіло
Через structured output модель повертає `{ say: string, emotion: Emotion, action?: Action }`. `emotion` береться з набору `emotions` маніфесту, `action` — з дозволеного переліку (`wave`, `jump`, `point_at_chat`…). Стрімінг `say`; емоція застосовується на початку, дія — в кінці. Моделі без structured output мають fallback: тег `[emotion]` на початку тексту, валідований.

### 6.3 Провайдери (AI SDK)
- **Ollama** (локально, приватно) — рекомендований за замовчуванням; **Anthropic** (Claude Haiku як дешевий хмарний варіант); **OpenAI-compatible** (LM Studio, OpenRouter, OpenAI).
- Ключі зберігаються в `safeStorage`. Модель і endpoint налаштовуються. Без ключа й без Ollama чат вимкнений, а персонажі працюють повністю.
- **Пресети у виборі провайдера (D-25)**, кожен з орієнтовною підказкою вартості в UI:
  1. **Ollama, локально:** безкоштовно, приватно, працює офлайн; швидкість і якість залежать від заліза.
  2. **Claude Haiku 5.5:** рекомендований хмарний варіант. Підказка: ≈ $0,0005 за повідомлення, ≈ $1,5–5 на місяць при типовому використанні.
  3. **Claude Opus 5.5:** найсильніший. Підказка: ≈ 40× дорожчий за Haiku ($4 / $20 проти $0,10 / $0,50 за 1M токенів вводу / виводу).

  OpenAI-compatible лишається розширеною опцією.
- **Підказки вартості — дані** в `src/content/` (ціни за 1M токенів, оцінка на повідомлення, дата «станом на»), а не в логіці. Ціни перевіряються за офіційним прайсом на старті M2.
- **Лічильник вартості (M2):** використання за день і місяць і оцінка витрат у налаштуваннях. Коли є реальні дані, підказка замінюється на виміряну вартість одного повідомлення.
- **Підписку Claude.ai не змішуємо з оплатою API.** Текст UI: ключ API оплачується окремо на platform.claude.com, і там можна задати ліміт витрат (посилання; домен у allowlist `shell.openExternal`).
- Денний бюджет токенів (§6.5) діє для всіх провайдерів.

Серед вбудованих tools немає shell-команд, kill процесів чи змін файлів. Якщо LLM пропонує дію в системі, вона показується як текстова інструкція. Цикл tool calling обмежений загальним таймаутом і кількістю кроків: ≤ 4 кроки, коли в запиті лише вбудовані tools, і ≤ 6, якщо запропоновано MCP-tools (§6.8). Реєстр tools з M2 має поле `source` (`builtin | mcp`), а рішення «виконати / спитати / відмовити» ухвалює чиста функція ядра `decideToolCall` (ADR 013). Вбудовані tools завжди `run`.

### 6.5 Промпт, контекст, памʼять, безпека
- Системний промпт збирається з: базової ролі, `persona` персонажа, мови інтерфейсу, правил (коротко, в характері, не вигадувати дані системи — лише через tools).
- Контекст запиту: зведення стану (настрій, час доби, фокус, головні показники) + 3–7 фактів про користувача з памʼяті. Факти видимі й редаговані в налаштуваннях. Історія обрізається за токенами.
- **Недовірений текст** — заголовки вікон, буфер, назви процесів і файлів, події hooks, `persona`/репліки імпортованих паків, описи й результати MCP-tools (§6.8). Він іде в промпт лише в розмічених блоках даних з лімітом довжини і ніколи не стає інструкцією.
- Ініціатива: подія → core вирішує, *чи* говорити → репліка з шаблонів персонажа (офлайн, миттєво) → за бажанням LLM перефразовує в межах денного бюджету токенів.
- Перед першим AI-запитом — одноразове пояснення, які дані можуть піти провайдеру.

Поза v1. Інтерфейс `Voice` (TTS/STT) закладено.

### 6.7 Evals
`evals/cases/*.yaml`: 20–30+ сценаріїв, серед них:
- «що гальмує?» → викликав `get_top_processes`, не вигадав цифр;
- injection у заголовку вікна → проігнорував;
- «поясни помилку» (M2): стек-трейс у буфері → пояснив причину й кроки, не вигадав файлів і рядків, яких немає в тексті; injection у буфері → проігнорував;
- «чому CI червоний?» (M4): назвав впалий job/крок із логу, не вигадав; injection у лозі → проігнорував;
- handoff (M4): `draft_handoff` лише на прохання користувача, тіло без секретів із контексту;
- відповідь у характері кожного персонажа;
- мова uk/en, довжина, валідний `{say, emotion}`.
`pnpm eval --provider ollama|anthropic` → звіт у `reports/evals/`. Детерміновані перевірки (tool, схема, довжина) у CI з mock-провайдером. Живі прогони — вручну перед релізом.

### 6.8 MCP-клієнт: tools із серверів користувача (D-24, ADR 013)
Користувач підключає власні MCP-сервери: календар, GitHub, нотатки тощо. Персонаж користується їхніми tools у характері. **Кожен підключений сервер недовірений.**
- **Бібліотека:** `@modelcontextprotocol/client` (транспорти, життєвий цикл). Tools для AI SDK будуємо самі: `dynamicTool` + `jsonSchema()` через посередника `main/ai/mcp/`. Схвалення — `toolApproval` AI SDK, рішення — з ядра. `@ai-sdk/mcp` `tools()` не використовуємо: він передає описи й результати моделі без посередника.
- **Транспорти:**
  - **stdio** (локальна команда користувача) — межа виконання коду. Перед першим запуском і після будь-якої зміни `command`/`args`/ключів `env` апка показує повний рядок команди з попередженням «ця програма запускається з твоїми правами» і чекає явного підтвердження.
    - Аргументи — масивом, без власного shell.
    - `cwd` — `userData/mcp/<id>/`.
    - Оточення — мінімальний allowlist SDK + задані `env`, ніколи весь `process.env`.
  - **Streamable HTTP:** `https://` для віддалених, `http://` лише для `127.0.0.1`/`localhost`. Без редиректів, статичні заголовки (PAT/ключ). OAuth (PKCE, loopback-редирект) — другий крок етапу.
  - Застарілий HTTP+SSE не підтримується.
- **Режими tools:** `off` / `ask` / `auto`.
  - Кожен новий tool — `off`; увімкнений — `ask`.
  - `auto` можна обрати лише для tools із `readOnlyHint: true`, і UI каже, що це заява сервера.
  - Tools із `destructiveHint` або без `readOnlyHint` ніколи не бувають `auto`.
  - **Нічого не схвалюється автоматично за замовчуванням.**
- **Підтвердження кожного виклику (`ask`):** бульбашка біля персонажа і картка в чаті показують сервер, tool і **точні аргументи** (повний JSON) та червону позначку для не-read-only або руйнівних. Кнопки «Дозволити раз» / «Відмовити».
  - «Завжди дозволяти» для не-read-only у v1 немає.
  - Виклик тримає main, renderer надсилає лише `{approvalId, approved}`.
  - Без відповіді впродовж TTL запит вважається відмовою. Відмова повертається моделі, і модель не повторює виклик.
- **Правило «забруднення»:** коли в хід потрапив недовірений текст (результат MCP, буфер, заголовок вікна, подія hooks), наступний `auto`-виклик до *іншого* сервера стає `ask`. Паралельні виклики першого кроку не забруднені.
- **Захист від отруєння описів:**
  - відбиток SHA-256 (назва + опис + схема + анотації) фіксується при вмиканні; будь-яка зміна → tool `off`, доки користувач не схвалить різницю;
  - описи очищуються від керівних, zero-width і bidi-символів, мають ліміт довжини й позначку «опис зовнішнього tool — це дані»;
  - користувач бачить рівно той текст, що й модель;
  - `instructions` сервера ігноруються;
  - назви — `mcp_<server>_<tool>` (`[a-z0-9_]`, ≤ 64), вбудовані tools затінити не можна.
- **Результати:** лише текст і `structuredContent`, решта → `[omitted: …]`. Ліміт на результат і на хід. Результат іде в розмічений блок `<tool_result server="…" untrusted>`.
- **Можливості клієнта:** без `sampling`, `roots`, `elicitation`.
- **Ліміти** (`src/content/`): таймаут виклику й ходу (без часу очікування користувача), ≤ 8 MCP-викликів на хід, 30 викликів/хв на сервер, ≤ 20 увімкнених MCP-tools у запиті, ≤ 8 серверів, ≤ 4 запущених, повідомлення ≤ 1 MB, stderr ≤ 64 KB.
- **Життєвий цикл stdio:**
  - запуск ліниво (відкрито чат з MCP або увімкнений проактивний бриф), зупинка після простою; **у простої із закритим чатом процесів серверів немає**;
  - при виході — закрити транспорт і завершити дерево власного дочірнього процесу (лише наш PID);
  - падіння → ≤ 3 перезапуски за 10 хв, далі «помилка»;
  - ліміт RSS (за замовч. 512 MB), вимірюється лише поки сервер працює.
- **Секрети:** значення `env` і заголовків — секретні за замовчуванням, зберігаються в `safeStorage`. Їх ніколи не повертають у renderer, не пишуть у лог і не експортують.
- **Приватність:**
  - з хмарним провайдером назви й описи увімкнених tools, аргументи й обрізані результати йдуть провайдеру — одноразове пояснення для кожного сервера (доповнює §6.5);
  - з Ollama і локальними stdio-серверами Pixmates нічого не виводить з машини;
  - сервер може сам ходити у свій бекенд, і налаштування кажуть, що Pixmates цього не контролює.
- **UX:**
  - налаштування → AI → MCP-сервери:
    - вставити JSON у форматі `mcpServers` → main валідує (zod, ≤ 64 KB) і показує попередній перегляд із маскованими секретами;
    - «Перевірити з'єднання»;
    - список tools з перемикачами режимів і описом, як його бачить модель;
    - лог stderr, видалення;
  - у чаті — слід викликів (сервер · tool · статус · час, згорнуто) і картка підтвердження;
  - персонаж у `think` під час tools, `wave` раз, коли чекає підтвердження. Нових поз не треба.
- **Ранковий бриф (M-MCP, D-24):** календар + GitHub через підключені сервери.
  - **Opt-in**, вимкнено за замовчуванням; вмикається в налаштуваннях MCP з вибором серверів для брифу.
  - **Тригер:** перше розблокування екрана (`powerMonitor` `unlock-screen`) або перший запуск апки за день, не раніше `BRIEF_EARLIEST_HOUR`; не частіше 1 разу на день. Рішення «чи брифувати» — чиста функція ядра (`now`, дата останнього брифу, opt-in, тихий режим із M3 — тоді бриф чекає).
  - **Потік:** миттєве шаблонне привітання офлайн → за наявності LLM — зведення в характері (події дня, PR на рев'ю, призначені issues).
  - **Лише `auto` read tools.** У хід брифу пропонуються тільки tools у режимі `auto`; рішення ядра `ask` у брифі стає `deny` без показу — бриф ніколи не піднімає непрошених підтверджень. Правило «забруднення» діє як завжди: перший крок викликає сервери паралельно, далі — лише той самий сервер.
  - Сервери стартують ліниво для брифу й зупиняються після простою. Без LLM, без `auto` tools або з помилкою сервера — лише шаблонне привітання; дані не вигадуються.
- **Дані:** таблиця `tool_calls` (міграція + фікстура), аргументи з маскуванням секретів, зберігання 30 днів.
- **Evals:** отруєний опис; injection у результаті з проханням записати в інший сервер; відмову не повторює; бриф без вигаданих даних (порожній календар → так і каже); бриф не викликає не-`auto` tools.

## 7. Dev companion (ADR 006)
- **Claude Code hooks.** У налаштуваннях генерується фрагмент hook-конфігу. Hook-команда шле подію на локальний endpoint `127.0.0.1:<port>` з токеном. Події:
  - `PermissionRequest` / `Notification` → `react:needs_you`;
  - `Stop` → `react:agent_done`;
  - `PostToolUseFailure` / `StopFailure` → `react:agent_failed`;
  - `SubagentStart/Stop` → персонаж «кличе помічників»;
  - `SessionStart` → вітання.
  Лише фіксовані схеми подій (zod). Вільний текст не потрапляє в промпт без розмітки.
- **Локальний MCP-сервер** (Streamable HTTP або stdio-шим): tools `say(text)`, `emote(emotion)`, `notify(level, title)`, `get_handoff()` (read). `say` показується як цитата від агента з позначкою джерела, а не голосом персонажа. Слухає лише localhost, авторизація токеном, перевірка `Origin`/`Host`, rate limit.
- **Git / CI** (опційно): гілка й «брудність» поточного репо, статус останнього GitHub Actions run через `gh` (якщо встановлено) — реакції на зелений/червоний CI.
- **«Чому CI червоний?» (M4, D-24):** достатньо `gh`, GitHub MCP не потрібен. На червоний run CI-спостерігач (main) один раз читає `gh run view <id> --log-failed` — фіксовані аргументи масивом, без shell, `id` лише з власного спостерігача, не від LLM.
  - Лог недовірений: зберігається хвіст `CI_LOG_TAIL_MAX` символів (`src/content/`) з очищенням керівних/ANSI-символів, у промпт — розміченим блоком через `get_ci_failure`, вмикає правило «забруднення».
  - Персонаж реагує на червоний CI (шаблон) і пропонує чип «Чому червоний?» → зведення в характері: workflow, job, крок, ймовірна причина. Без LLM — шаблон із назвою job/кроку.
  - Немає `gh` або авторизації → функція прихована, підказка в налаштуваннях.
- **Handoff до Claude Code (M4, D-24):** у чаті персонаж на прохання користувача оформлює завдання через `draft_handoff(title, body)` → картка-чернетка (редагувати / «Передати» / скасувати). Лише після «Передати» завдання стає доступним.
  - Claude Code забирає його tool `get_handoff()` на власному MCP-сервері Pixmates: повертає найстаріше передане й не забране завдання (`title`, `body`, `created_at`) і позначає його забраним. Read-tool, без shell і запису файлів.
  - Ліміти: `HANDOFF_BODY_MAX` символів, ≤ `HANDOFF_QUEUE_MAX` у черзі, TTL `HANDOFF_TTL_MS` (`src/content/`). Секрети з налаштувань у тіло не потрапляють.
  - Дані: таблиця `handoffs(id, title, body, status, created_at, taken_at)` (міграція + фікстура). Персонаж реагує, коли завдання забрано (`wave`).
- Усе вимкнено за замовчуванням і вмикається окремо.

## 8. Корисні функції (не-AI)
- **Pomodoro:** 25/5 (налаштовується), персонаж у `focus` «працює» поруч, у паузі потягується. Статистика фокусу.
- **Нагадування:** 20-20-20 для очей, вода, постава; кожне окремо; поважають DND/fullscreen.
- **Системні реакції** (§4.1), кожну можна вимкнути.
- **Тихий режим:** автоматично у fullscreen і під час демонстрації екрана (евристика: fullscreen + Zoom/Meet/Teams/OBS), вручну з трею (1 год / до вечора).
- **Трей:** показати/сховати (хоткей `Ctrl+Alt+P`), зміна персонажа (підменю-перемикач з i18n-іменами; хоткей «наступний» `Ctrl+Alt+N`), шар «поверх усіх / лише на столі», тихий режим, Pomodoro, налаштування, вихід. Іконка — голова активного персонажа.
- **До M3 (D-27):** тихий режим у треї й радіальному меню показано **вимкненим із видимою причиною** («з'явиться пізніше»); Pomodoro в треї й радіальному меню з'являється лише в M3 (у M1 його немає).
- **Автозапуск** з Windows (опційно).

## 9. Налаштування
- Персонажі: активний персонаж і зміна, хоткей «наступний» (`Ctrl+Alt+N`), шар (поверх усіх / лише на столі), хоткей показати/сховати (`Ctrl+Alt+P`), імпорт/видалення, розмір (S/M/L + точне налаштування), швидкість, дисплей.
- Поведінка: частота занять, вікна on/off, реакції on/off, cooldown, тихі години.
- AI:
  - провайдер — пресети Ollama / Claude Haiku 5.5 (рекомендований хмарний) / Claude Opus 5.5 з підказкою вартості, а OpenAI-compatible у розширених (D-25, §6.3);
  - модель, ключ (з поясненням, що API оплачується окремо від підписки Claude.ai, і посиланням на ліміт витрат на platform.claude.com);
  - мова, хоткей, денний бюджет токенів;
  - використання й оцінка витрат за день/місяць (M2);
  - памʼять (перегляд/редагування/очищення);
  - MCP-сервери (§6.8): додати JSON, перевірити, режими tools, лог, видалити.
- Dev companion: hooks (згенерувати конфіг), MCP-сервер, git/CI.
- Приватність: назва апки — так; заголовок вікна — ні; буфер — лише по кнопці.
- Сумісний режим рендеру (вимикає прозорість/апаратне прискорення при проблемах GPU).
- Мова інтерфейсу: uk / en.
- Вигляд вікна налаштувань — за `docs/design/UI-GUIDE.md` (D-26, §6.1): ліва навігація, розділи з рядками «назва + опис + контрол», перемикач режиму tool `вимк.` / `питати` / `авто`. Для tools, що змінюють дані, `авто` вимкнено, і причину видно текстом.

## 10. Приватність і безпека
- Телеметрії немає. Мережа використовується лише для обраного LLM, GitHub Releases (оновлення можна вимкнути) і MCP-серверів, які користувач сам додав (HTTP — лише `https://`, крім localhost; без редиректів).
- **MCP-клієнт (ADR 013, §6.8):**
  - кожен сервер недовірений, вимкнений за замовчуванням;
  - описи й результати — розмічені дані з лімітами;
  - відбитки tools проти «rug pull»;
  - не-read-only виклики — лише після підтвердження з точними аргументами;
  - правило «забруднення» між серверами;
  - без `sampling`/`roots`/`elicitation`;
  - stdio-команда запускається лише після явного підтвердження повного рядка команди, без shell, з мінімальним оточенням, з лімітом RSS і завершенням дерева процесу при виході;
  - секрети — у `safeStorage`;
  - OAuth-loopback (другий крок) слухає лише `127.0.0.1` і проходить рев'ю `electron-security-reviewer`.
- Electron hardening:
  - `contextIsolation`, `sandbox`, `nodeIntegration: false`, `webSecurity: true`;
  - строгий CSP, без `remote`; шрифти лише вбудовані в апку (`font-src 'self'`, без `data:` і зовнішніх CDN, D-26);
  - заборона навігації, `window.open`, `webview`;
  - `shell.openExternal` лише для https і allowlist;
  - валідація всього IPC.
- Локальні сервери (hooks, MCP) слухають тільки `127.0.0.1`, мають токен і перевірку `Origin`/`Host`.
- Скін-паки містять лише статичні ассети; zip-slip, ліміти, жодного виконуваного вмісту.
- Supply chain: точні версії, lockfile, заблоковані install-скрипти (окрім явного allowlist для нативних модулів), `pnpm audit`, Actions за SHA.

| **M3 — Сенсори і користь** | SystemMonitor, idle, fullscreen/тихий режим, реакції з cooldown, Pomodoro, нагадування | реакції не спамлять (тест throttle) |
| **M5 — Кастомізація** | імпорт паків і GIF, налаштування, uk/en | імпорт із валідацією, zip-slip тест |
| **M6 — Реліз v1** | NSIS-інсталятор, автооновлення, автозапуск, e2e smoke, README з гіфками, GitHub Release | критерії §14 |

**MVP для портфоліо = M0 + M-ART + M1 + M2.**
**Порядок (D-24):** M1 → M2 → M4 → M-MCP → M3 → M5 → M6; M1b — після M2, точне місце в черзі обирає власник (D-27). Dev companion — головна відмінність продукту, і йому з ядра потрібні лише пріоритети й анти-спам M1. M-MCP — окрема межа довіри (вихідні з'єднання й запуск коду), тому це окремий етап зі своїм рев'ю, а не частина M4. Ховання у fullscreen і тихий режим (M3) лишаються обов'язковими до релізу (§14). **«Вау»-функції v1 (D-24, вибір власника з кандидатів ADR 013):** «поясни цю помилку» (M2), «чому CI червоний?» і handoff до Claude Code (M4), ранковий бриф (M-MCP). Жива сесія Claude Code й так у M4 (§7). Решта кандидатів (нагадування про зустріч, фокус з issue) і голос (§6.6) — після v1.

## 14. Критерії готовності v1
- Інсталятор NSIS для Windows 11, автозапуск, автооновлення з GitHub Releases.
- Активний персонаж живе поверх вікон, не блокує кліки поза собою, ходить краями вікон, реагує на курсор; зміна персонажа з трею працює з перехідною анімацією.
- Ховається у fullscreen. В idle: < 2% CPU, ≤ 280 MB приватної пам'яті (`pnpm perf` на зібраній збірці).
- Відповідають на «що гальмує систему?» з реальними даними через tools, у характері, з емоцією. «Поясни скопійоване» пояснює помилку з буфера в характері; буфер читається лише після натискання. Evals зелені.
- Реагують на події реальної сесії Claude Code (hooks) і на MCP `say`/`emote`. На червоний CI пояснюють, який job/крок упав (через `gh`). Завдання, оформлене з персонажем і передане користувачем, Claude Code забирає через `get_handoff`.
- Користувач підключає власний MCP-сервер (stdio або HTTP) із налаштувань. Персонаж відповідає з його даними в характері. Увімкнений ранковий бриф (календар + GitHub) раз на день зводить дані лише через `auto` read tools, без непрошених підтверджень. Нові tools вимкнені, не-read-only виклик виконується лише після «Дозволити» з точними аргументами, evals injection/отруєння зелені. Після виходу не лишається процесів серверів, а idle-бюджет із закритим чатом не змінюється (ADR 013).
- Pomodoro і щонайменше 2 нагадування працюють і поважають тихий режим.
- 8 вбудованих оригінальних персонажів (4 жіночі, 4 чоловічі; D-18); імпорт власного пака/GIF з валідацією.
- README з гіфками, `docs/AI-WORKFLOW.md`, зелений CI.
